## [v1.0.0] - 2026-11-08

- BREAKING: The pre-1.0 API is removed: `RestClient`, `GraphQLClient`, `BaseClient`, `ClientConstants`, the `Anvil.Queries` classes, the `Anvil.Payloads.Request` and `Anvil.Payloads.Response` types, and `AnvilClientException`'s `HttpStatusCode`, `ResponseHeaders` and `Data["Message1"]` (use `StatusCode`, `Headers` and `Errors`). "Upgrading from 0.x" in the README maps each one to its replacement.
- BREAKING: One `AnvilClient` replaces `RestClient` and `GraphQLClient`. One `HttpClient` pipeline sends REST and GraphQL requests, so auth, rate limiting, retries and errors are the same for both. The `GraphQL.Client` dependency is gone, and with it a transitive `System.Text.Encodings.Web` 4.7.0 flagged as a critical vulnerability. The package targets `netstandard2.0` and `net10.0`.
  - `new AnvilClient(new AnvilClientOptions { ApiKey = ..., BaseUrl = ... })` sends every request to one host: REST to `{BaseUrl}/api/...`, GraphQL to `{BaseUrl}/graphql` (no longer `https://graphql.useanvil.com`). `BaseUrl` defaults to production. `new AnvilClient(apiKey)` reads `ANVIL_API_KEY` from the environment when the key is null.
  - OAuth access tokens are supported: `new AnvilClientOptions { AccessToken = ... }`. JWTs are sent as-is, other tokens base64 encoded, like node-anvil.
  - BREAKING: The API key is now sent as `Basic base64(apiKey + ":")`, with the trailing colon node-anvil and python-anvil send. It was sent without it.
  - Rate limits are learned from the first response that carries the `X-RateLimit-Limit` and `X-RateLimit-Interval-Ms` headers. Requests made before the first response arrives wait for it. The client counts requests over a sliding window, like the API, and only waits when the limit has been reached. Every client in the process with the same `BaseUrl` and credentials shares one limiter. A `429` is retried after its `Retry-After` plus 50ms, or after a second when there is no usable `Retry-After`, for as long as it takes; the `RateLimited` event reports each one, and `RateLimit` the current limit.
  - Every request is retried on `500`, `502`, `503` and `504`, and when it couldn't connect, up to `MaxRetries` times (5) with exponential backoff from 100ms. A request that was sent but got no response in time throws `TimeoutException` and is not retried, since the API may have processed it.
  - Requests time out after 5 minutes by default (`Timeout`, also per request through `RequestOptions`). They never did before. An `HttpClient` or `HttpMessageHandler` can be passed in, e.g. to use a proxy.
  - BREAKING: `AnvilClientException` is structured: `Errors` holds the normalized errors (GraphQL errors, REST errors and validation errors with their `Fields`), `StatusCode` the status (0 when there was no response), `Headers` the headers and `ResponseData` any partial GraphQL `data`. Its message is `"{status}: {name}: {message} (field: message, ...)"`. An error is any status outside 2xx, or a 2xx GraphQL response with `errors`; a non-JSON error, like a `502` from a proxy, keeps the start of its body.
  - `RequestGraphQLAsync(query, variables)` returns the response's `data` (or deserializes it to a type), and `RequestRestAsync(method, path, json)`, `RequestRestBytesAsync`, `RequestRestStreamAsync` and `SendRestAsync` send any REST request, like node-anvil's `requestGraphQL` and `requestREST`. A full URL is accepted if it is on the client's `BaseUrl`, and refused otherwise. `AnvilClient.VERSION_LATEST` and `VERSION_LATEST_PUBLISHED` are the special version numbers.
  - The `User-Agent` is `dotnet-anvil/{version}`, configurable with `UserAgent`.
- `AnvilClient` has every method node-anvil has: `FillPdfAsync`, `GeneratePdfAsync` and `DownloadDocumentsAsync` return `byte[]`, with `*StreamAsync` and `*ToFileAsync` variants; `CreateEtchPacketAsync` and `GetEtchPacketAsync` return a typed `EtchPacket`, `ForgeSubmitAsync` a `Submission`, `GenerateEtchSignUrlAsync` the URL and `RemoveWeldDataAsync` whether the data was removed, plus `GetCurrentUserAsync`. Each takes its payload as a typed `Anvil.Payloads` object, an anonymous object, a dictionary, a `JObject` or a JSON string. `FillPdfAsync` sends `versionNumber` whenever one is given, including `0`.
- The GraphQL operations in `Anvil.GraphQL.Operations` match node-anvil's exactly, variable for variable, and are validated against the API schema in CI. `createEtchPacket` gains `organizationEid`, `enableEmails`, `createCastTemplatesFromUploads`, `duplicateCasts` and `allowUpdates`; `forgeSubmit` gains `enforcePayloadValidOnCreate` and `webhookURL`. `CreateEtchPacketAsync` and `ForgeSubmitAsync` take a `responseQuery` (the fields to return, with or without braces) and a whole `mutation`; `GetEtchPacketAsync` and `GetCurrentUserAsync` a `responseQuery`. BREAKING: the default response fields follow node-anvil: `documentGroup.id` and `weldData.id` are dropped (they are not in the API schema; use `eid`), `forgeSubmit` adds `status`, `continueURL` and `payloadValue`, and `createEtchPacket` adds `status`, `isTest`, `allowUpdates`, `numberRemainingSigners`, `webhookURL` and the timestamps. `forgeSubmit` loses the `errorType` variable, which the API never had.
- Add `AnvilClient.PrepareGraphQLFile` for multipart uploads of a path, bytes or a stream, anywhere in a mutation's variables under a `file` key: in a `DocumentUpload` passed to `CreateEtchPacketAsync`, or in the variables of any mutation sent with `RequestGraphQLAsync`, like `createCast`'s `$file: Upload!` ([#26](https://github.com/anvilco/dotnet-anvil/issues/26)). The request is sent per the GraphQL multipart request spec, and sent again after a `429` (a path is reopened and a seekable stream rewound). Base64 files in a `Base64Upload` are still sent inline as JSON. The variables are checked the way node-anvil checks them: a file may only sit under a `file` key, and a `file` must be a prepared file, a base64 object with `data`, `filename` and `mimetype`, or a `url` object.
- `Anvil.Payloads` has typed payloads built on the generated types, so every option the API documents is available: `FillPdfPayload`, `GeneratePdfPayload` (with `MarkdownContent`, `MarkdownTable`, `HtmlContent`, `Logo`), `CreateEtchPacketPayload` (`IsDraft = false`, `IsTest = true` by default), `ForgeSubmitPayload`, `EtchSigner` with all its options, `SignerField`, `SignatureField`, `Rect`, `Base64Upload`, and the files `EtchCastRef`, `DocumentUpload`, `DocumentMarkup` and `DocumentMarkdown`. An `in-person` signer is accepted ([#27](https://github.com/anvilco/dotnet-anvil/issues/27)).
- Add `Anvil.Types`: C# types generated from the API's OpenAPI spec and GraphQL schema, the .NET counterpart of `@anvilco/types` and `python_anvil.types`. `Anvil.Types.Rest` has the REST request bodies, `Anvil.Types.GraphQL` every type in the schema (its `File` is `AnvilFile`, so it doesn't clash with `System.IO.File`), and `Anvil.Types.Operations` the arguments of every query and mutation, like `CreateEtchPacketArgs`. They are regenerated whenever the API's published specs change; a regeneration that removes or changes a type is released as a major.
- The package ships XML docs, a symbols package and Source Link, and depends on Newtonsoft.Json 13.0.4.
- The README documents every method, option and error, and has an upgrade guide from 0.x. The examples are a project: `dotnet run --project examples -- fill`.
- Development:
  - Add `test-client/`, a console app that runs every client method against a real environment: `ANVIL_API_KEY=... dotnet run --project test-client`.
  - Add a dependency on the published `@anvilco/types` package, which ships the API's GraphQL schema and OpenAPI spec, and `dev/check-graphql.mjs`, which validates the client's queries and mutations against the schema.
  - A Sync API Types workflow bumps `@anvilco/types` and regenerates `Anvil.Types` whenever anvil-js publishes a new version, opening a PR when anything changed. A sync of a major `@anvilco/types` release, one where the API removed or changed types or fields, is marked BREAKING, so the next release is a major.
  - The unit tests run the client against a real HTTP server on a loopback port as well as a scripted handler, so the auth encoding, multipart bodies, rate limit timing, retries and error handling are checked on the wire. CI fails when line coverage of the hand-written code drops below the threshold in `ci.yml`.
  - Publishing to NuGet is done by the Publish workflow when a version tag is pushed, after a maintainer approves it, with NuGet trusted publishing or a `NUGET_API_KEY` secret; `dev/release.sh` prepares and tags a release. CI packs the package, validates it with the .NET SDK's package validation, and installs it into a scratch app.
  - CONTRIBUTING.md covers development, the integration test script, the generated types, versioning and publishing. The examples are built in CI.
  - Line endings are LF, and `.gitattributes` keeps them that way.
  - Update the test dependencies (xunit 2.9, Microsoft.NET.Test.Sdk 18, coverlet 10). Moq was unused and is removed.
