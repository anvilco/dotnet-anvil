# Contributing

How to work on the client and publish it. For using the client, see the [README](README.md).

## Development

The client targets .NET Standard 2.0 and .NET 10, and `global.json` pins the .NET SDK to develop with (any 10.0 feature band). The tests, the examples, the test-client and the dev tools target .NET 10.

Build, run the unit tests and check the formatting from the `src` directory:

```sh
cd src
dotnet build
dotnet test
dotnet format --verify-no-changes
```

`dotnet format` fixes what the formatter can. The settings are in `.editorconfig`. Warnings are errors in every project (`Directory.Build.props`).

Run a single test class or test with a filter:

```sh
dotnet test --filter "FullyQualifiedName~HttpTests"
dotnet test --filter "FullyQualifiedName~UploadsTests.AFilePath_IsSentAsMultipart"
```

The tests in `src/AnvilTests/HttpTests.cs` run the real client against a local HTTP server (`Support/LoopbackServer.cs`), so the auth encoding, multipart bodies, rate limit timing, retries and error handling are checked on the wire. The rest script an `HttpMessageHandler` (`Support/FakeHandler.cs`). CI fails when line coverage of the hand-written code drops below the threshold in `.github/workflows/ci.yml`; the generated `src/Anvil/Types` are excluded as data. To see the coverage locally:

```sh
dotnet test /p:CollectCoverage=true /p:Include="[Anvil]*" /p:ExcludeByFile="**/Types/GraphQL/*.cs%2c**/Types/Operations/*.cs%2c**/Types/Rest/*.cs"
```

The `examples/` project, the `test-client/` and `dev/DumpOperations` are not in the solution; CI builds them so they can't rot:

```sh
dotnet build examples
dotnet build test-client
```

## Testing against a real environment

[`test-client/`](test-client/Program.cs) runs every method against an Anvil environment and prints a `PASS`, `FAIL` or `SKIP` for each. Run it on a release before and after a change to see which behaviors changed. It uses staging by default, and needs an API key for that environment:

```sh
ANVIL_API_KEY=<your staging API key> dotnet run --project test-client
```

* `ANVIL_BASE_URL` - _optional_ Test another environment instead, e.g. `http://localhost:3000`.
* `ANVIL_ACCESS_TOKEN` - _optional_ An OAuth access token for the same environment, to test Bearer auth. Skipped when not set.
* `ANVIL_PDF_TEMPLATE_ID` - _optional_ The PDF template to test `FillPdfAsync` with. Defaults to the first template in your organization that has example data.
* `ANVIL_FORGE_EID` - _optional_ The webform (Forge) in a Workflow to test `ForgeSubmitAsync` with. Defaults to the first one in your organization.

Everything it creates is test data. It creates test Etch packets each run, and removes the Workflow submission it creates.

## The GraphQL operations and the generated types

The API's specs, the GraphQL schema and the OpenAPI spec, ship with the [`@anvilco/types`](https://www.npmjs.com/package/@anvilco/types) npm package, an exact-pinned dependency of `dev/`. anvil-js regenerates the package from production after every deploy, and node-anvil and python-anvil generate from the same copy, so every client describes the same API build. No API key needed. (A version of the package that predates the OpenAPI spec shipping in it falls back to `schema/openapi.json`, fetched from production by `dev/fetch-schema.sh`.)

```sh
dev/fetch-schema.sh      # bump @anvilco/types to the latest published version
cd dev && npm ci         # once; the dev scripts need Node.js 24 and the graphql package
npm run check:graphql    # validate the client's operations against the schema
npm run generate         # regenerate src/Anvil/Types from the specs
npm run check:generated  # fail if src/Anvil/Types is out of date with the specs
```

The client's queries and mutations live in `src/Anvil/GraphQL/Operations.cs` and are node-anvil's documents, variable for variable. `check:graphql` dumps them with `dev/DumpOperations` and validates each against the schema; CI runs it, so an operation that no longer matches the API fails the build rather than a request.

`src/Anvil/Types` is generated by `dev/generate-types.mjs` from those specs: `Anvil.Types.Rest` (the REST request bodies), `Anvil.Types.GraphQL` (every type in the schema) and `Anvil.Types.Operations` (the arguments of every query and mutation). `npm run generate` runs offline, and CI fails if the generated files don't match the specs, so run it after `dev/fetch-schema.sh` or after changing the generator. Dependabot leaves `@anvilco/types` alone; the sync workflow owns that bump, since it regenerates the types with it. The hand-written payloads in `src/Anvil/Payloads` extend the generated classes (they are `partial`), so a change there is usually a matter of adjusting an override.

The [Sync API Types workflow](.github/workflows/sync-api-types.yml) does both steps whenever anvil-js publishes a new `@anvilco/types` (its release workflow sends an `anvilco-types-published` dispatch here), and weekly as a backstop, and opens a PR when anything changed. It needs a `CI_GITHUB_TOKEN` repository secret: a token that can push branches and open PRs, so the PR gets its CI checks (the workflow's own `GITHUB_TOKEN` can't trigger workflows). python-anvil and anvil-js use the same secret name.

## Publishing

Publishing to NuGet is done by the [Publish workflow](.github/workflows/publish.yml) when a version tag is pushed, in two steps: the workflow builds, tests and packs the release, and a maintainer approves the publish job. Merging to `main` does not publish anything.

1. On a branch, bump the version and release the `[Unreleased]` section of `CHANGELOG.md`:
   ```sh
   dev/release.sh prepare 1.0.0
   ```
   This sets `<Version>` in `src/Anvil/Anvil.csproj`, renames `[Unreleased]` to `[v1.0.0]` with today's date, and commits. If you're on `main`, it creates a `release/v1.0.0` branch first. Push the branch, open a PR, and merge it to `main`.
2. Tag that commit on `main` and push the tag:
   ```sh
   git checkout main && git pull
   dev/release.sh tag
   ```
   This checks that `main` is up to date with `origin/main`, that `v1.0.0` doesn't already exist, and that `CHANGELOG.md` has a `[v1.0.0]` section, then tags and pushes.
3. When the workflow's build job has finished, approve its publish job on the workflow run's page. The job then publishes the package and its symbols to NuGet and creates the GitHub release, with that version's CHANGELOG section as the notes.

Both commands accept `--dry-run`. For a pre-release, run `dev/release.sh prepare 1.0.0-rc.1`: it bumps the version but leaves `CHANGELOG.md` alone, so the notes stay under `[Unreleased]` for the final release. Pre-releases are `1.0.0-alpha.1`, `1.0.0-beta.1` or `1.0.0-rc.1`, tagged `v1.0.0-rc.1`, and marked as pre-releases on GitHub.

When testing the workflow, only publish pre-release versions. A version can't be unpublished from NuGet, only unlisted.

`dev/pack-smoke.sh` packs the library and installs the package into a scratch console app, which CI runs on every PR, so what gets published is exercised and not just the project reference.

### Setup

Done once per repository:

* **The `nuget` environment.** On GitHub, under the repository's Settings > Environments, create `nuget` with required reviewers: the maintainers who may approve a publish. The publish job waits for one of them.
* **Credentials**, one of:
  * **NuGet trusted publishing** (preferred, no secret): on nuget.org, under the `Anvil` package owner's Trusted Publishing settings, add a policy for the `anvilco/dotnet-anvil` repository, the `publish.yml` workflow and the `nuget` environment. Then set a `NUGET_USER` repository variable to the nuget.org username that owns the policy. The workflow logs in with `NuGet/login`, which exchanges the job's OIDC token for a short-lived API key.
  * **An API key**: a `NUGET_API_KEY` repository secret with a nuget.org API key scoped to push `Anvil`. Used when `NUGET_USER` is not set.
