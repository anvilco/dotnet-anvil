# Contributing

How to work on the client and publish it. For using the client, see the [README](README.md).

## Development

The client targets .NET Standard 2.0 and .NET 10, and `global.json` pins the .NET SDK to develop with (any 10.0 feature band). The tests, the examples, the test-client and the dev tools target .NET 10.

Build, run the unit tests and check the formatting from the `src` directory:

```sh
cd src
dotnet build
dotnet test --framework net10.0
dotnet format --verify-no-changes
```

The tests also target `net48`, so they run against the package's `netstandard2.0` build, the one .NET Framework apps get, on .NET Framework's HTTP stack. That needs Windows: on macOS and Linux pass `--framework net10.0`, and CI's "Test on .NET Framework 4.8" job runs the `net48` tests. On Windows, a plain `dotnet test` runs both.

`dotnet format` fixes what the formatter can. The settings are in `.editorconfig`. Warnings are errors in every project (`Directory.Build.props`).

Run a single test class or test with a filter:

```sh
dotnet test --framework net10.0 --filter "FullyQualifiedName~HttpTests"
dotnet test --framework net10.0 --filter "FullyQualifiedName~UploadsTests.AFilePath_IsSentAsMultipart"
```

The tests in `src/AnvilTests/HttpTests.cs` run the real client against a local HTTP server (`Support/LoopbackServer.cs`), so the auth encoding, multipart bodies, rate limit timing, retries and error handling are checked on the wire. The rest script an `HttpMessageHandler` (`Support/FakeHandler.cs`). CI fails when line coverage of the hand-written code drops below the threshold in `.github/workflows/ci.yml`; the generated `src/Anvil/Types` are excluded as data. To see the coverage locally:

```sh
dotnet test --framework net10.0 /p:CollectCoverage=true /p:Include="[Anvil]*" /p:ExcludeByFile="**/Types/GraphQL/*.cs%2c**/Types/Operations/*.cs%2c**/Types/Rest/*.cs"
```

The `examples/` project, the `test-client/` and `dev/DumpOperations` are not in the solution; CI builds them so they can't rot:

```sh
dotnet build examples
dotnet build test-client
```

## Testing against a real environment

[`test-client/`](test-client/Program.cs) runs every method against an Anvil environment and prints a `PASS`, `FAIL` or `SKIP` for each. Run it on a release before and after a change to see which behaviors changed. It uses staging by default, and needs an API key for that environment:

```sh
ANVIL_API_KEY=<your staging API key> dotnet run --project test-client
```

* `ANVIL_BASE_URL` - _optional_ Test another environment instead, e.g. `http://localhost:3000`.
* `ANVIL_ACCESS_TOKEN` - _optional_ An OAuth access token for the same environment, to test Bearer auth. Skipped when not set.
* `ANVIL_PDF_TEMPLATE_ID` - _optional_ The PDF template to test `FillPdfAsync` with. Defaults to the first template in your organization that has example data.
* `ANVIL_FORGE_EID` - _optional_ The webform (Forge) in a Workflow to test `ForgeSubmitAsync` with. Defaults to the first one in your organization.

Everything it creates is test data. It creates test Etch packets each run, and removes the Workflow submission it creates.

## The GraphQL operations and the generated types

The API's specs, the GraphQL schema and the OpenAPI spec, ship with the [`@anvilco/types`](https://www.npmjs.com/package/@anvilco/types) npm package, an exact-pinned dependency of `dev/`. anvil-js regenerates the package from production after every deploy, and node-anvil and python-anvil generate from the same copy, so every client describes the same API build. No API key needed. (A version of the package that predates the OpenAPI spec shipping in it falls back to `schema/openapi.json`, fetched from production by `dev/fetch-schema.sh`.)

```sh
dev/fetch-schema.sh      # bump @anvilco/types to the latest published version
cd dev && npm ci         # once; the dev scripts need Node.js 24 and the graphql package
npm run check:graphql    # validate the client's operations against the schema
npm run generate         # regenerate src/Anvil/Types from the specs
npm run check:generated  # fail if src/Anvil/Types is out of date with the specs
```

The client's queries and mutations live in `src/Anvil/GraphQL/Operations.cs` and are node-anvil's documents, variable for variable. `check:graphql` dumps them with `dev/DumpOperations` and validates each against the schema; CI runs it, so an operation that no longer matches the API fails the build rather than a request.

`src/Anvil/Types` is generated by `dev/generate-types.mjs` from those specs: `Anvil.Types.Rest` (the REST request bodies), `Anvil.Types.GraphQL` (every type in the schema) and `Anvil.Types.Operations` (the arguments of every query and mutation). A GraphQL type whose name matches a type in a namespace .NET projects import by default would make that name ambiguous for anyone importing `Anvil.Types.GraphQL`, so the generator renames it (`GRAPHQL_RENAMES`: `File` is `AnvilFile`), and a test fails when the schema adds another. `npm run generate` runs offline, and CI fails if the generated files don't match the specs, so run it after `dev/fetch-schema.sh` or after changing the generator. Dependabot leaves `@anvilco/types` alone; the sync workflow owns that bump, since it regenerates the types with it. The hand-written payloads in `src/Anvil/Payloads` extend the generated classes (they are `partial`), so a change there is usually a matter of adjusting an override.

The [Sync API Types workflow](.github/workflows/sync-api-types.yml) does both steps whenever anvil-js publishes a new `@anvilco/types` (its release workflow sends an `anvilco-types-published` dispatch here), and weekly as a backstop, and opens a PR when anything changed. The PR says whether the sync crosses a major, minor or patch release of `@anvilco/types` (see Versioning), worked out from the version `dev/package.json` pinned before and after; on a major it marks its changelog note `BREAKING`, adds the `breaking` label, and asks the GitHub users in the optional `SYNC_BREAKING_REVIEWERS` repository variable (comma separated) for review. It needs a `CI_GITHUB_TOKEN` repository secret: a token that can push branches and open PRs, so the PR gets its CI checks (the workflow's own `GITHUB_TOKEN` can't trigger workflows). python-anvil and anvil-js use the same secret name.

## Versioning

Versions follow [semver](https://semver.org). The generated `Anvil.Types` are public API, so they count: a release that removes or renames a type, member or argument is a major, one that adds them is a minor. Once a major's baseline is set (see Publishing), package validation enforces it for the whole package, generated types included: `dotnet pack`, and so CI, fails on any breaking change against that release.

The generated types come from `@anvilco/types`, which takes its own bumps from the API's spec diffs ([its policy](https://github.com/anvilco/anvil-js/tree/main/packages/types#versioning): major for a removed or changed type, field or argument, minor for additions, patch for descriptions). So every sync sets a floor for the next release here: a sync across a `@anvilco/types` major is a `BREAKING:` entry in `CHANGELOG.md` and the next release is a major; a minor makes it at least a minor. The client's own changes can raise the bump, never lower it.

A deliberate break, such as merging a breaking sync, fails `dotnet pack` until it is accepted: run `dotnet pack src/Anvil -c Release /p:GenerateCompatibilitySuppressionFile=true`, which writes each break to `src/Anvil/CompatibilitySuppressions.xml`, review the file and commit it with the change. After the next major is published and the baseline moves to it, delete the file.

## Publishing

Releases are run from [anvilco/package-ops](https://github.com/anvilco/package-ops), the private repository that releases every Anvil package: Actions → **Release** → **Run workflow**, pick `anvilco/dotnet-anvil` and the increment. Merging to `main` does not publish anything, and nothing in this repository publishes.

The run checks out `main`, builds and runs the net10.0 tests (CI runs the net48 tests on every PR), checks the release floor (the last tag matches `<Version>` in `src/Anvil/Anvil.csproj`, `CHANGELOG.md` has notes under `[Unreleased]`, and the increment isn't below what the synced `@anvilco/types` demands; see Versioning), then bumps the csproj, turns `[Unreleased]` into `[vX.Y.Z] - date`, commits `Release vX.Y.Z` to `main`, tags `vX.Y.Z`, creates the GitHub release with that changelog section as its notes, packs, and pushes the package and its symbols to NuGet with [trusted publishing](https://learn.microsoft.com/en-us/nuget/nuget-org/trusted-publishing). `dotnet pack` runs package validation against the baseline release, so a breaking change fails there, before anything is pushed. A dry run (the default) shows all of that and changes nothing; run one first.

After publishing a new major (2.0.0, ...), set `<PackageValidationBaselineVersion>` in `src/Anvil/Anvil.csproj` to it and delete `src/Anvil/CompatibilitySuppressions.xml`, in a PR to `main`; the run's summary says so. From then on `dotnet pack`, and so CI, fails on any breaking change against that release: a removed or changed public type or member. A deliberate break waits for the next major, which moves the baseline. The baseline is 1.0.0. Package validation downloads it from NuGet, so a pack needs network access to nuget.org.

`dev/pack-smoke.sh` packs the library and installs the package into a scratch console app, which CI runs on every PR, so what gets published is exercised and not just the project reference.

Who may run a real release, the NuGet trusted publishing policy (for the `useanvil` account), and the GitHub App that pushes the release commit are set up in package-ops; its README has the details and how to add a repository.
